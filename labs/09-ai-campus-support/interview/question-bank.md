# 实验九面试追问

## 为什么不能把原始私人问题和 Token 直接发给模型？

模型供应商不是授权边界，也不需要身份凭证。服务先把私人问题分类为固定模板，在 legacy 内用原始 Token 做对象级授权，只把最小状态留在本地编排；模型请求只包含安全模板和已审阅公开规则。这样既减少数据外发，也避免提示注入把 Token 或交易详情带出系统。

## AI 客服为什么只能读，不能自动退款或裁决？

退款、争议和质保会改变资金、库存和权利义务，必须继续经过原有鉴权、幂等、状态机、事务和审计边界。模型输出是不确定文本，只能解释规则；即使回答正确，也不能替代写命令的业务前置条件和可信外部证据。

## 如何同时避免越权枚举和模型幻觉？

对象级权限由交易服务判断，无权与不存在统一 404；AI 层不从不同错误中推断资源是否存在。回答依据来自带来源版本的公开规则片段，检索不到、模型超时或依赖不可用就明确失败，不用常识补写交易事实。本人状态作为结构化字段返回，与生成文本分离。

## 为什么模型、规则索引和交易状态要有三种独立故障语义？

交易状态是事实源，授权或下游失败不能伪造成“没有订单”；规则索引不可用时没有可引用依据；模型不可用时已有事实和规则也不代表能生成回答。三者分别返回可诊断但脱敏的错误，前端显示中文重试提示，恢复后重试只读请求，不缓存虚构答案。

## 前端为什么只在内存保存 Token？

客服页面不需要跨刷新保持登录。内存会话缩短 Token 暴露窗口，401 时立即清空并回到登录态；代价是刷新后需要重新登录。浏览器只访问同源 Gateway 路径，不把 Token 放进 URL、日志、localStorage 或 Playwright 报告。

## 8.2 为什么先拆商品读取而保留交易事实？

搜索结果天然可以从完整商品事件重建，允许短时延迟；库存扣减、订单金额和退款仍需要市场库的本地事务。读服务只对查询负责，交易服务在原事务内写不可变 `schemaVersion=2` 快照 Outbox，不把发布时重新查询到的较新状态冒充过去事件。订单快照继续由订单事务保存。

## 8.2 为什么既有 Inbox 又有商品版本？

同一 eventId 重发由 Inbox 去重，不同 eventId 可能按乱序抵达。同商品的 `aggregateVersion` 条件更新防止旧事件覆盖新投影；同事务写 index Outbox 让 MySQL 已提交的变化即使 ES 暂停也不会丢失。ES 写入使用外部版本和 tombstone，旧索引待办也不能复活售罄商品。

## 8.2 如何在在线重建时防止丢事件和误删索引？

重建先在读库一致性快照中固定 `sequence_no` 高水位并建新索引，再补放高水位后的待办；门禁的数据库 generation、owner、token 和租约阻止旧 owner 切换。读写别名原子更新，旧索引清理作为持久任务，删除前检查当前 live 别名。Rabbit replay 只是重新投递完整源事件，不能替代读侧索引高水位补放。

## 8.2 新读服务收到零条源事件时何时可搜索？

零事件不等于源库已经回放完毕。源端仍须确认发布高水位为 0 的完成屏障，读端记录 replay ID 和高水位，等对应索引待办清空且专用人工失败队列为空后才 READY。搜索请求也检查同一健康状态；否则投影库刚建立、Rabbit 故障或死信积压时返回 503。

## 为什么先拆身份服务？

身份接口和交易用例的职责清楚，验证码、密码验证、Token 签发可以独立部署。先拆这一边界能练习服务发现、网关和跨进程认证，同时保留库存、支付、退款与售后在一个交易数据库事务内，避免同时引入分布式资金事务。

## Gateway 已经认证，业务服务为什么再次验签？

业务服务可能被直接访问，也不能将客户端可构造的 Header 当成可信身份。两层分别验证身份服务的 RS256 签名和 `kid/iss/aud/sub/roles/iat/exp` 契约，业务权限始终从 Token 得到。Gateway 清理伪造身份 Header 只是入口防护的一部分。

## 为什么用 RS256 和 JWKS？

身份服务独占私钥，资源服务器只获得公钥，降低验证服务被攻破后伪造 Token 的风险。JWKS 通过 `kid` 选择公钥；未知密钥不能作为放行理由。代价是需要管理公钥获取、缓存、轮换和冷启动失败语义。

## 身份服务停机后，业务请求能否继续？

已缓存公钥且 Token 未过期时可以继续验签，登录依赖身份服务仍会失败。冷启动没有可用公钥时不能放行。必须分别验证热缓存、冷启动、未知 `kid` 和恢复，不把一次正常请求当成所有故障场景的证据。

## liveness 已经 UP，为什么 readiness 仍可能 DOWN？

liveness 只说明进程能响应探针，readiness 还要检查 JWKS 中可用的 RS256 公钥与 Eureka 注册中心/必需实例。JWKS 最近成功探测只缓冲 30 秒，Eureka 缓冲 45 秒，超过窗口或实例为空就 DOWN。探针缓存与 JWT decoder 的密钥缓存是独立的；短窗口内 readiness 的 UP 不保证一个此前未验签的 Token 首次请求会成功，因此冷启动和热缓存必须分别测试。

## 为什么禁止 Gateway 自动重试写请求？

连接中断不等于下游事务未提交，重试注册、验证码或交易命令可能产生重复副作用。原交易用例的显式幂等键继续负责重放语义；网关不替客户端重建写请求，也不返回虚构的成功结果。

## 如何证明数据库所有权不是口头约定？

身份和交易分别使用本库迁移账号与运行账号，运行账号只授予必要 DML 权限。真实 MySQL 测试分别尝试跨库读取并断言被拒绝；生产业务模块不依赖对方领域模型，不用跨库外键或查询补足事务。

## 截止调度和筹资为什么可能死锁？

若截止扫描先锁状态/截止时间二级索引再等待主键，筹资先锁主键再更新索引，就形成反向等待。候选扫描只读取提示列表，逐项事务按主键加锁，再用当前状态、金额与数据库截止时间条件更新。回归测试应控制真实主键锁，观察目标记录等待，不能通过吞掉数据库异常来宣称串行化。

## 为什么单独服务能启动，聚合旅程却在自动配置阶段失败？

聚合旅程把多个服务的 classes 和运行时依赖放进同一测试 JVM，各 Spring 上下文虽然独立，自动配置仍看到共享类路径。JDBC 依赖会让无数据库的 Gateway 或 Eureka 尝试创建 DataSource；Gateway 自动配置也可能装入 Servlet 服务。应显式限定每个应用的自动配置边界，保持各自 YAML、WebApplicationType、数据库和注册名，再用真实端口与 lb 路由旅程验证。不能通过给网关补假数据库或跳过启动测试掩盖边界问题。

## 为什么提交 .gitignore 仍不能阻止本地密钥进入 Docker 构建上下文？

Git 和 Docker 使用不同的忽略规则。被 Git 忽略的 `.env`、密钥和日志仍可能通过 build context 传给 daemon；需要 `.dockerignore` 独立限制。若 Dockerfile 复制预打包 JAR，应仅放行所需运行 JAR，排除测试 JAR、报告和其他构建产物，并实际构建验证规则未破坏 COPY。
