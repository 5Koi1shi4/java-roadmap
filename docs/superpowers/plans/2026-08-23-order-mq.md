# 订单状态机与 RabbitMQ 可靠消息 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 创建可独立运行和验证的订单状态机与 RabbitMQ 可靠消息实验，保证延迟取消、Outbox 发布、消费幂等与失败重试均可观察和复现。

**Architecture:** 订单、库存和 Outbox 在同一 MySQL 事务中变更；调度器以租约领取 Outbox 事件并经 RabbitMQ publisher confirm 发布。事件通过按延迟桶划分的 TTL 队列死信转发到消费者；消费者以租约化的消费记录协调重复投递，并将业务变更和完成标记置于同一事务中。

**Tech Stack:** JDK 17、Spring Boot 3.5.5、Spring JDBC、Spring AMQP、MySQL 8、RabbitMQ 3、Flyway、JUnit 5、Mockito、Testcontainers。

## Global Constraints

- 新项目位于 `labs/04-order-mq`，不改动前三个实验的业务代码。
- JDK 固定为 17；Maven 使用该实验自带的 Maven Wrapper。
- 订单状态仅允许 `PENDING_PAYMENT → PAID` 与 `PENDING_PAYMENT → CANCELLED`。
- 所有状态更新用包含原状态的条件 SQL；不得先查状态再无条件写回。
- 事件模型固定为 `OrderTimeoutEvent(UUID eventId, String eventType, long orderId, Instant occurredAt, int schemaVersion)`，首版 `eventType=ORDER_TIMEOUT`、`schemaVersion=1`。
- Outbox 领取使用 `NEW → PUBLISHING` 条件更新和过期租约接管；确认成功才置为 `PUBLISHED`。
- 消费消息只在业务事务提交后确认；去重记录以 `event_id` 唯一约束协调，`COMPLETED` 重复消息直接确认，过期 `PROCESSING` 才能接管。
- 数据库/MQ 连接与短暂锁冲突可重试三次；消息格式、事件版本、字段校验和非法状态不重试，直接进入人工处理死信队列。
- TTL 队列按延迟桶分开：10 秒、1 分钟、5 分钟；每桶只设置一个固定 TTL。本实验的订单超时走 1 分钟桶。
- 单元测试不得启动 Spring；MySQL、RabbitMQ、Flyway 与监听链路通过 Testcontainers 集成测试验证。每个集成测试生成独立 UUID 并在 `@BeforeEach` 清理表数据。
- 每项行为按红—绿循环开发：先运行失败测试，再写最小实现，再运行同一测试通过。

public OrderStatus pay(OrderStatus status) {
    if (status != PENDING_PAYMENT) throw new IllegalOrderTransitionException(status, PAID);

public OrderStatus cancelExpired(OrderStatus status) {
    return status == PENDING_PAYMENT ? CANCELLED : status;
}

- [ ] **Step 3: 声明固定 TTL 桶与死信路由**

声明 `order.timeout.exchange`、`order.timeout.1m.queue`、`order.cancel.exchange`、`order.cancel.queue` 和 `order.manual.queue`。1 分钟桶设置 `x-message-ttl=60000` 与 `x-dead-letter-exchange=order.cancel.exchange`；10 秒和 5 分钟桶分别为 10000 和 300000。业务路由键固定为 `order.timeout.1m`，不向同一个队列发送不同 TTL 的消息。

- [ ] **Step 4: 实现消费租约和事务完成边界**

消费者事务中以 `event_id` 插入 `PROCESSING` 记录；唯一键冲突后：`COMPLETED` 直接返回、未过期 `PROCESSING` 抛 `RetryableMessageException`、过期 `PROCESSING` 用条件更新接管。调用 `OrderService.cancelExpired` 后，同一事务把记录更新为 `COMPLETED`。事务抛出异常时不得确认消息，也不得留下完成标记。

- [ ] **Step 5: 实现异常分类和有限重试**

`InvalidOrderEventException`、`JsonProcessingException`、`IllegalOrderTransitionException` 归为不可重试；`AmqpConnectException`、`TransientDataAccessException` 和死锁/锁等待异常归为可重试。监听器使用三次尝试、固定 1 秒退避；可重试次数耗尽与不可重试异常均使用 recoverer 发送到 `order.manual.queue`，携带 `failure-category` 与 `failure-message` header。
