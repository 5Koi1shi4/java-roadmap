# 实验九：Java AI 智能校园客服设计

## 1. 目标与范围

实验九学习 Java 服务中的检索增强生成、受控模型接入、跨服务只读授权，以及从浏览器到服务端可复跑的全栈验收。第一阶段提供校园交易规则问答，以及已登录用户本人订单、普通售后案件和质保案件的状态查询。回答应能指出所依据的规则版本；模型无法证明的结论不得冒充交易事实。前端完成注册/登录、客服问答、本人资源选择和状态展示的使用闭环，不重建商品发布、支付、交付或管理控制台。

实验使用独立分支 `learning/ai-campus-support`，活动树只包含根 `.gitignore` 和 `labs/09-ai-campus-support/**`。从实验八已验收提交 `177cd25` 建立独立实验基线，原实验八分支和目录保持不变。文档中心 `main` 只保存设计、计划、进度和验收入口，不合并实验代码。实验九支持全新实验环境，不提供生产不停机迁移。

第一阶段不创建聊天系统、长期会话记忆、工单、人工转接、自动仲裁、自动退款、改价、支付、证据读取或任何其他交易命令；正式 CAS、真实支付和物流仍不在范围内。不把本实验的开发与测试环境当作真实个人信息处理方案或生产上线许可。

## 2. 技术基线和依赖

- JDK 17、Maven Wrapper、Spring Boot `3.5.16`、Spring Cloud BOM `2025.0.3` 保持实验八基线。
- Spring AI 固定 `1.1.8`。其 1.1.x 系列对应 Spring Boot 3.5.x；2.0.x 对应 Spring Boot 4，不与当前基线混用。
- 前端固定 React `19.3`、TypeScript、Vite `8.3.0`，使用满足 Vite 要求的 Node.js（`20.19+` 或 `22.12+`）；版本由 lockfile 锁定，不依赖全局 npm 包。浏览器验收使用锁定版本的 Playwright Chromium。
- 对话模型和嵌入模型使用可配置的外部 API 适配器；密钥只从运行环境获取，仓库只保存占位符。`test` 和 `verify` 使用本地受控 HTTP 模型替身，无真实密钥或公网模型调用。
- 规则向量索引使用独立的 Elasticsearch 索引，不复用商品 SmartCN 索引；交易事实仍以 `market_db` 为唯一事实源，AI 服务不得连接 `market_db`、`identity_db` 或 `product_read_db`。
- 通过 Testcontainers 验证 Elasticsearch、MySQL、真实 HTTP 和服务发现协作；需要 Docker 的完整验收不能以 skipped 测试代替。

## 3. 服务边界

`labs/09-ai-campus-support/` 继承实验八的独立可运行聚合工程，在其中加入 `ai-support-service` 和 `support-web/`。Eureka 显式发现该服务；Gateway 仅把精确的客服 POST 路径转发给它，现有身份、商品搜索和交易路由保持原契约。浏览器只访问前端站点同源的 `/api/**` 代理，由代理转发到 Gateway，不直连内部服务或持有服务密钥。AI 服务与 Gateway、交易服务分别自行验证 RS256 JWT 的签名、issuer、audience 和有效期，不信任传入的用户 ID Header。没有用户 Token 只能询问公开规则；查询私人订单或案件必须持有有效 Token。

AI 服务只依赖三个接口：`PolicyRetriever` 返回版本化公开规则片段；`TradeStatusReader` 向兼容交易服务发起携带原始 Bearer Token 的内部只读请求；`AnswerModel` 根据受控上下文生成规则解释。这三个接口在应用层分别使用，领域对象不依赖 Spring、数据库、Elasticsearch 或模型 SDK。交易服务新增最小只读状态端点，在自身数据库内以 `resource_id` 和 JWT `user_id` 同时过滤。AI 服务无订单或案件的共享表、数据库账号、通用 SQL 查询和交易写工具。

现有质保案件 GET 已具有本人访问校验，但订单缺少只读 GET；本实验需要为订单与普通售后补足同等边界的最小投影，并复用质保授权语义。为免用户手填 UUID，交易服务还提供本人订单、普通售后及质保案件的有界分页列表；SQL 必须按 JWT `user_id` 过滤，不返回任何其他用户的资源。列表与单项读取均不得触发状态迁移。对已认证用户，单项不存在或不属于本人一律返回相同 404；管理员角色不自动绕过私人案件授权。交易服务故障返回 503，不能解释为资源不存在。内部状态响应只含类型、当前状态、必要的业务时间和规则解释所需的非敏感字段，不含邮箱、地址、交易描述、证据、支付凭据、文件 URL 或内部对象 key。

## 4. HTTP 契约与回答路径

`POST /api/ai/support/answers` 消费和返回 `application/json; charset=UTF-8`。请求是严格反序列化的 JSON：非空中文或英文 `question`（UTF-8 长度上限 2 KiB）、可选 `orderId` 或 `caseId` UUID、可选 `caseType`（仅 `DISPUTE`/`WARRANTY`）。一次请求最多指定一个私人资源；`caseId` 必须同时给出 `caseType`。未知字段、非法 UUID、非法范围、互斥字段或非法枚举返回 400。资源 ID 由前端本人列表中明确选择或客户端明确提供，模型不得从自然语言猜测 ID、枚举用户资源或选择新的数据查询。

响应包含 `answer`、`sources`（服务端认可的规则来源 ID、标题和版本）以及可选的 `status`（类型和状态摘要）。规则来源由检索器选择并由服务端附加，不能接受模型自报的来源。私人状态由交易服务验证后由应用层确定性呈现。私人资源请求不把原始问题传给外部模型：仅从受控规则问题分类中选择通用询问模板；若无法安全分类，只返回已授权的确定性状态和资料不足提示。发送给模型的上下文不包含用户标识、订单/案件 UUID、证据、支付信息或自由文本交易描述。公开规则问题经长度校验后发送，服务端仍不记录完整问题、模型提示、响应正文、Token 或私人状态。

规则检索先于模型调用。如果没有满足阈值且版本有效的规则片段，直接返回明确的“没有足够依据”，不让模型凭常识生成规则；有私人资源时仍可返回已授权的确定性状态。检索或模型故障分别返回稳定的 503，不返回原始供应商错误体；授权资源查询若返回 404，则请求直接返回统一 404，不调用模型。外部模型请求有固定超时、有限并发和预算上限，不做无界重试。公开问答与私人查询使用分开的限流额度；超额为 429。

交易服务为前端和 AI 服务提供 `GET /api/support/orders`、`/api/support/disputes`、`/api/support/warranties` 三个本人列表，以及对应的 `GET /api/support/{type}/{id}` 单项摘要。列表按创建时间和 ID 稳定排序，使用不透明游标、默认 10 条且最多 20 条；游标不能跨用户或资源类型复用。所有响应显式使用 UTF-8 JSON。AI 服务只调用单项摘要，前端只用列表让用户选择已授权的资源。

## 5. 客服前端与使用流程

`support-web/` 是独立的 React/TypeScript 应用。页面只覆盖公开规则问答、校园邮箱注册与登录、本人订单/售后选择、状态与规则解释、登出；不构建商品交易或管理页面。未登录访客可以提出规则问题，但私人资源列表入口提示登录。登录后用户从有界本人列表选择一个资源、输入问题并查看状态卡和规则来源。状态由确定性数据区域展示，规则解释与来源单独展示，不能把模型文本伪装成官方裁定。

注册沿用身份服务的验证码、注册和登录接口。本地 Compose 为手动浏览器演示增加显式 `demo-mail` Profile，只将身份服务的邮件适配器定向到本地邮件捕获服务，用户从其本地界面查看验证码；既有 `local` 内存邮件适配器在其他运行方式中保持原行为。不增加公开的验证码读取 API，也不把验证码写入日志。自动浏览器验收使用测试邮件夹具。前端只把短期 Access JWT 保存在当前页面的内存状态，刷新或关闭页面需重新登录；不写入 `localStorage`、`sessionStorage`、URL、日志或浏览器错误报告。对 API 401 清除内存登录状态并引导重登录；403、404、429、503 分别显示可行动的中文提示，不展示下游原始错误。

开发时 Vite 和生产静态站点均以同源 `/api/**` 转发到 Gateway，前端不接触 Eureka 或内部服务地址。生产构建由独立静态容器提供，SPA 路由只回退到自身 `index.html`，`/api/**` 不回退或缓存；静态资源使用内容哈希缓存，含私有状态的 JSON 与 HTML 禁止共享缓存。浏览器显示规则来源和状态时按纯文本渲染，不将模型输出作为原始 HTML 注入 DOM。

界面以校园服务台为主题：主区域是问题与答复，旁侧呈现规则来源卡及本人状态时间线；小屏改为单列并保留清晰的“规则解释”和“当前状态”标题。中文文案说明资料不足、查询失败、登录过期和重试路径。输入控件有可见标签，键盘可完成登录、选择资源与问答，焦点可见；触控目标至少 44px、正文至少 16px，颜色对比度至少 4.5:1，并尊重 `prefers-reduced-motion`。

## 6. 规则资料与检索

知识源只取仓库中经人工审定、版本化的交易规则 Markdown，不摄入 README 中的历史设想、开发日志、用户聊天、订单备注、案件陈述或文件证据。每段保留稳定 `sourceId`、标题、规则版本和内容摘要；切分在标题或段落边界，不跨规则语义。索引构建只处理公开规则，嵌入由可配置适配器生成；测试用确定性嵌入替身。索引与源版本不匹配时就绪状态为 DOWN，查询返回 503；重建使用新索引和校验后的别名切换，失败继续保留已验证的旧版本，不把混合版本作为已就绪。

检索结果作为不可信资料内容包围在明确的引用边界内。提示词要求模型只能解释引用中的规则，不能服从资料中关于改变角色、访问私有数据或执行操作的指令。引用校验和私人授权仍由服务端完成，提示词不承担安全边界。

## 7. 测试与验收

先写失败测试，再做最小实现。单元测试验证请求构造、规则版本和引用、资料不足、模型故障、严格解码、资源互斥、本人列表游标、状态确定性呈现与敏感字段过滤。真实 HTTP 集成测试验证匿名规则问答、本人订单/售后列表及单项查询、他人和不存在资源同构 404、无效身份 401、模型替身收到的数据最小集合、中文响应正文和 `application/json; charset=UTF-8`。故障测试验证交易服务、Elasticsearch、模型替身分别不可用时的状态、恢复及无误判 404；同时回归实验八的身份、商品搜索和交易路径。

前端使用纯逻辑和组件测试验证请求参数、Access JWT 内存生命周期、状态/规则来源分离显示、错误提示与安全文本渲染；Playwright Chromium 在桌面与移动视口完成“注册/登录 → 规则问答 → 本人订单/售后选择 → 问答与状态 → 登出”的真实浏览器旅程，并验证键盘操作、401 重登录、他人资源不可见、模型/交易故障和页面恢复。浏览器验收必须访问实际构建的前端及同源 Gateway 代理，不能只对前端 API mock 宣称全栈通过。

在 JDK 17 下执行目标实验目录的 `mvnw.cmd test` 和 Docker 可用后的 `mvnw.cmd verify`，确认 Surefire 与 Failsafe/Testcontainers 无 failures、errors、skipped；前端运行 `npm ci`、`npm test`、`npm run build` 和真实环境的 `npm run test:e2e`，并执行 `git diff --check`。Testcontainers/Compose 前先只读运行 `docker info`，仅手动启动需要的 Docker Desktop，不启动历史本机 MySQL、Redis 或全套服务。验收文档记录实际 JDK、Node、镜像版本、命令、测试计数、浏览器旅程、外部替身与故障恢复证据；README、排障记录、学习日志和面试追问共同构成闭环。完成验收后再更新 `main` 的实验九状态。
