# 项目文档与全实验面试题库设计

## 目标

在 `main` 分支完成一次可公开发布的文档重构：把实验九明确标记为全栈实验，补齐实验一至九的面试题库，并将项目介绍、设计流程、技术选型、技术取舍与算法说明迁移到独立项目手册。另在本机生成一份面试用项目经验/实习经验材料，但该文件必须完全排除在 Git 索引、提交和远端历史之外。

公开文档必须以仓库现有代码、SQL、配置、测试、验收记录和独立实验分支为事实来源。不能把规划中的能力写成已经实现，不能虚构生产流量、公司背景、业务收入或线上事故数据。

## 交付边界

### 公开并推送到 GitHub `main`

- 修改根 `README.md`，把实验九标注为“全栈实验”，并增加项目手册入口。
- 重构 `interview/question-bank.md`，只保留 AI 生成声明、实验分组、问题、参考回答、代码/测试证据与必要追问。
- 新建 `docs/project-handbook/README.md`，作为整个项目的完整介绍与手册索引。
- 新建 `docs/project-handbook/design-process.md`，解释需求、边界、数据流、故障模型、验证和实验演进流程。
- 新建 `docs/project-handbook/technology-stack.md`，解释技术栈的用途、选择理由、优点、缺点和替代方案。
- 新建 `docs/project-handbook/algorithms-and-tradeoffs.md`，解释仓库实际使用的算法、并发控制与可靠性机制。

### 仅保留在本地

- 新建 `local-only/interview/project-experience.md`。
- 通过仓库本地 `.git/info/exclude` 忽略 `local-only/`；不得修改受版本控制的 `.gitignore` 来公开这个本地交付路径。
- 文件不得被 `git add`、不得进入任何提交、不得推送，也不得在公开文档中链接。
- 公司、岗位、时间、学校等未知个人信息使用明显占位符；成果数据仅采用仓库可验证数据，不虚构生产指标。

## 题库设计

### 结构与纯度

`interview/question-bank.md` 顶部只保留标题和以下含义明确的声明：题库由 AI 根据仓库实现与测试生成，仅供学习和面试准备参考，使用者应结合实际代码验证。其后直接进入实验一至九的题目，不保留技术取舍表、项目介绍、学习路线、复习计划或其他说明性附录。

每道题采用一致结构：

1. 问题标题。
2. `参考回答`：直接回答原理与本项目做法。
3. `代码/测试证据`：指向真实类、SQL、配置或测试。
4. `追问`：仅在能帮助澄清边界或代价时保留。

题号全文件连续编号。实验八分为 8.1 身份服务拆分与 8.2 商品读模型拆分，但仍属于实验八章节。实验九单独成章，不能继续挂在实验七之后。

### 覆盖范围

题库目标为 90 题，分配如下：

| 实验 | 主题 | 题数 |
| --- | --- | ---: |
| 1 | JWT、RBAC、刷新令牌与安全边界 | 10 |
| 2 | Redis 缓存、一致性、穿透/击穿/雪崩与降级 | 8 |
| 3 | 秒杀、库存、限流、幂等与并发控制 | 8 |
| 4 | 订单状态机、RabbitMQ、Outbox/Inbox 与重试 | 10 |
| 5 | Elasticsearch、中文检索、外部版本与在线重建 | 10 |
| 6 | MinIO、安全文件、去重、ACL、租约与清理 | 8 |
| 7 | 校园交易、支付/退款、争议、质保与恢复演练 | 12 |
| 8 | Spring Cloud、RS256/JWKS、Gateway、读模型与就绪门禁 | 14 |
| 9 | 全栈 AI 客服、RAG、最小披露、只读授权与浏览器闭环 | 10 |

现有高质量问题应保留其事实内容并统一格式；缺失题目优先从相应独立分支的 README、题库、验收文档和测试中补齐。实验九题目还需覆盖规则版本与引用、提示注入边界、结构化交易事实与生成文本隔离、限流/超时以及桌面和移动端真实浏览器验收。

## 项目手册设计

### `docs/project-handbook/README.md`

说明项目定位、九个实验的递进关系、分支隔离模型、整体能力地图、从浏览器/客户端到服务与基础设施的高层数据流、主要安全和可靠性原则，以及其余手册文档的阅读入口。明确这是教学与可复现实验项目，不宣称生产部署或真实第三方资质接入。

### `docs/project-handbook/design-process.md`

按“需求与风险识别 → 领域/服务边界 → 事实源与派生数据 → 状态机与并发不变量 → 外部依赖失败语义 → 安全与隐私 → 可观测性 → 测试与验收”解释设计流程。结合九个实验说明能力如何从单体安全服务演进到缓存、秒杀、可靠消息、搜索、文件、交易平台、Spring Cloud 拆分和全栈 AI 客服。

### `docs/project-handbook/technology-stack.md`

按运行平台、Web/安全、数据存储、缓存与限流、消息、搜索、对象存储、微服务、AI、前端、容器和测试分类。每项技术至少说明：项目中的职责、选择理由、优点、缺点、替代方案及不适用边界。版本号只在仓库能证实时列出，并说明不同实验分支可能固定在不同版本。

### `docs/project-handbook/algorithms-and-tradeoffs.md`

详细解释并联系代码证据：密码哈希与令牌摘要、Redis Lua 固定时间桶限流、缓存一致性策略、条件更新与乐观并发、库存扣减、状态机、幂等键与请求摘要、Outbox/Inbox、指数/固定退避、租约与 claim-token fencing、TTL/DLX、外部版本与 tombstone、游标分页、引用计数、内容哈希、在线索引重建与高水位补放、对象级 ACL、RAG 检索与来源约束。对每种机制说明它解决的问题、核心步骤或伪代码、时间/空间或运行代价、优缺点以及常见误用。

## 本地面试材料设计

`local-only/interview/project-experience.md` 包含：

- 30 秒和 2 分钟项目介绍。
- 简历项目经历版本，突出个人负责内容但不冒充生产团队成果。
- 实习经历表达模板，未知公司、岗位、日期和团队信息使用占位符。
- 4–6 个基于仓库真实实现的 STAR 案例。
- 可量化但可验证的指标，例如实验数量、测试数量、全栈 E2E 场景数量和故障恢复轮数。
- 高频追问与诚实边界，明确哪些能力是实验实现、哪些只是未来演进。

该文件可引用本地仓库路径帮助准备，但不得包含真实密钥、Token、个人联系方式或未提供的隐私信息。

## 验证与发布

公开变更完成后执行：

1. `git diff --check`，确保没有空白错误。
2. 检查题库章节、连续题号、90 题总数及实验一至九覆盖。
3. 检查题库不存在“技术取舍速记”等非题库章节。
4. 检查项目手册所有相对链接和提及的公开文件存在。
5. 扫描公开变更中的高置信密钥、Token、私钥头和本机绝对路径。
6. 用 `git check-ignore -v local-only/interview/project-experience.md` 证明本地材料由 `.git/info/exclude` 排除。
7. 用 `git status --porcelain` 证明本地材料未进入待提交集合。
8. 提交公开文档，刷新远端 `main` 并确认只做快进推送。
9. 推送后用远端引用确认 GitHub `main` 指向新提交。

## 验收标准

- 根 README 明确称实验九为全栈实验，并能进入项目手册和实验九分支。
- 面试题库包含实验一至九共 90 道有证据的题目，顶部明确 AI 生成、仅供参考。
- 面试题库除声明、实验标题、问题、回答、证据和追问外不含项目说明或技术取舍附录。
- 项目手册完整覆盖项目介绍、设计流程、技术选型、技术取舍、算法与各项优缺点，并区分已实现与可选演进。
- 公开变更不包含敏感信息或本机私有路径。
- 本地项目经验/实习经验文件存在、内容可用，但 Git 完全忽略且远端不可见。
- GitHub `main` 最终包含全部公开文档变更。
