# 实验四：订单状态机与 RabbitMQ 可靠消息设计

## 目标

构建独立、可重复验证的 Spring Boot 实验：订单可在待支付、已支付和已取消之间按规则迁移；未支付订单经 RabbitMQ 延迟消息自动取消；重复消息与失败重试不会造成重复释放库存。

## 范围与约束

- 使用 JDK 17、Spring Boot 3.5.5、MySQL 8、RabbitMQ 3、JUnit 5 与 Testcontainers。
- 创建 `labs/04-order-mq` 作为独立 Maven 项目，不改动前三个实验。
- 所有订单状态更新均使用带原状态条件的 SQL，避免并发覆盖。
- 每个领域事件使用全局唯一 `eventId`；消费去重记录与订单取消、库存释放在同一数据库事务中提交。
- 使用 RabbitMQ TTL 队列加死信交换机实现延迟取消；文档明确其延迟不精确、同队列不同 TTL 可能队头阻塞的限制。
- 消费端仅有限重试；重试耗尽进入人工处理死信队列，不无限重试。
- 新行为先以失败测试定义，随后实现最小代码；完整验收使用 `mvnw.cmd verify`。

## 架构

应用分为四层：

- `domain`：`Order`、`OrderStatus` 与 `OrderStateMachine`。状态机只负责合法迁移与幂等判断，不依赖 Spring、数据库或 RabbitMQ。
- `application`：`OrderService` 编排建单、支付与超时取消，并定义事务边界。建单时与订单一起保存 Outbox 事件。
- `infrastructure.persistence`：JDBC 仓储负责订单、库存、Outbox 和已消费事件。`cancelIfPending` 只匹配 `PENDING_PAYMENT`，库存释放只发生在更新成功时。
- `infrastructure.mq`：Outbox 发布器将待发布的超时事件发送至 TTL 队列；死信路由至超时消费者。消费者依 `eventId` 去重，并调用应用服务。

## 数据模型与消息流

订单表保存订单号、商品、数量、当前状态与时间戳；库存表保存可用库存；Outbox 表保存 `event_id`、事件类型、JSON 载荷、发布状态与失败信息；`consumed_message` 表以 `event_id` 为唯一键记录已完成的消费。

1. 创建订单事务：条件扣减库存，插入 `PENDING_PAYMENT` 订单，并写入唯一的 `ORDER_TIMEOUT` Outbox 事件。
2. Outbox 发布器读取未发布事件，经 publisher confirm 成功后标记已发布；确认失败保留未发布状态并记录失败原因，以便下次调度重试。
3. 超时事件进入 TTL 队列；过期后由死信交换机路由至取消队列。
4. 消费者处理时先插入消费记录；若重复键冲突则确认消息并直接返回。首次处理在同一事务中执行“仅取消待支付订单”和“仅对实际取消的订单释放库存”。
5. 瞬时消费者异常最多重试三次；超过次数路由到人工处理死信队列，并保留原消息及失败原因。

## 状态规则与错误处理

`PENDING_PAYMENT → PAID` 和 `PENDING_PAYMENT → CANCELLED` 是仅有的业务迁移。已取消订单支付必须返回业务冲突；已支付订单接收超时事件时保持已支付；重复超时取消保持已取消且不再释放库存。

创建订单库存不足时返回明确业务错误且不生成订单或 Outbox 事件。Outbox 发布失败不会回滚已提交订单，而是由后续发布调度补偿。消息消费未知异常不确认消息，由监听器的有限重试策略处理；重试耗尽后进入死信队列供人工排查。

## 验证策略

- 单元测试：状态机验证支付、取消、非法支付、已支付超时及重复取消。
- 持久化集成测试：验证状态条件更新、Outbox 与订单原子写入、同一 `eventId` 去重及库存最多释放一次。
- RabbitMQ 集成测试：使用 MySQL 与 RabbitMQ Testcontainers 验证 TTL 延迟取消、重复事件、消费者失败后的有限重试与死信路由。
- 文档验收：README 提供环境、启动、验证、消息拓扑与 TTL/DLX 边界；学习日志和题库记录可靠消息与幂等的取舍。

## 非目标

本实验不引入 RabbitMQ 延迟消息插件、分布式事务、订单支付网关或跨服务调用；它们不利于聚焦订单状态与可靠消息的核心闭环。
