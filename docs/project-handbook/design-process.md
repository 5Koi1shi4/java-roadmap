# 设计流程与实验演进

本页说明本仓库如何把学习目标变成可审查的边界、可验证的规则和可恢复的实现。它不是生产运行手册：`main` 只维护文档入口，代码、测试与验收记录在各实验独立分支中。设计结论以 [设计规格](../superpowers/specs/) 、[实施计划](../superpowers/plans/) 和实验 README 的实现及验收记录为证据；计划中的能力会明确标为未来工作。

## 1. 从业务目标识别风险

- **决策输入：** 先把“能完成一次业务动作”拆成会导致错误结果的风险。例如校园交易不只包含下单，还包括超卖、重复命令、支付结果未知、超时与用户操作竞争、私有证据泄露，以及搜索或消息组件暂时不可用。
- **仓库例子：** [实验七设计](../superpowers/specs/2026-08-30-campus-market-design.md) 将一口价交易限定为可审计的订单、库存、支付、履约和仲裁闭环；[实验九设计](../superpowers/specs/2026-09-16-ai-campus-support-design.md) 把 AI 客服限定为公开规则解释和本人状态只读查询，而非交易执行者。
- **防止的失败：** 避免将页面流程或模型回答误当成交易事实，或为了“功能完整”在未定义资金、授权和责任边界时加入自动退款、裁决、真实支付或真实身份接入。
- **验证证据：** 每个实验的 README 都列出范围、非目标和验收入口；实验七、八、九的验收记录将真实 HTTP、故障恢复和回归测试作为结论的一部分，而不是只以接口能返回成功为依据。

## 2. 划分领域、服务与数据所有权

- **决策输入：** 按“谁维护规则、谁写入事实、谁可以提供公开契约”划分，而不是按控制器或表的便利性划分。跨边界前，先确认是否仍需同一事务保护；若需要，暂不拆分写侧。
- **仓库例子：** 实验七采用模块化单体，让身份、商品库存、订单、支付、履约仲裁和审计各自拥有领域对象与表；实验八只先提取身份服务和商品读服务，交易库仍维护库存扣减、订单快照和售后规则。商品读服务拥有自己的投影库和索引，AI 服务不连接交易库，只经已授权的只读 HTTP 契约取得最小状态。
- **防止的失败：** 防止共享数据库把内部表变成隐式 API，或在库存与订单尚依赖本地原子提交时，过早迁走写侧而把正确性变成未证明的跨库补偿。
- **验证证据：** [渐进拆分设计](../superpowers/specs/2026-09-11-spring-cloud-progressive-split-design.md) 与 [商品读服务设计](../superpowers/specs/2026-09-15-product-read-service-design.md) 规定独立数据库、最小账号和不共享领域模型；实验八 README 的跨服务旅程和跨库访问边界测试提供验收证据。

## 3. 区分事实源、缓存与派生索引

- **决策输入：** 对每类数据先回答“能否作为交易决定依据”“能否从别处重建”“丢失后如何追赶”。只有受事务与业务规则保护的数据才是事实源；为性能或发现而存在的数据必须承认可滞后。
- **仓库例子：** MySQL 保存订单、库存、金额、截止时间和在售集合等事实源；Redis 只服务验证码、限流和缓存，Elasticsearch 是可重建搜索读模型，商品读服务是由事件构建的派生投影，MinIO 保存对象但逻辑授权仍由数据库记录决定。商品事实和 Outbox 在同一事务提交，读侧以版本、tombstone 和重放收敛。
- **防止的失败：** 防止用缓存或搜索结果判断可售库存，避免索引故障时把“查询不到”误判为“商品不存在”，也避免投影重建后被乱序旧事件覆盖。
- **验证证据：** [Elasticsearch 设计](../superpowers/specs/2026-08-24-elasticsearch-search-design.md) 和商品读服务设计要求一致性快照、高水位补放、外部版本与原子别名切换；README 中的重建、停机恢复和在售集合核对把这些规则纳入验收。

## 4. 建立状态机和并发不变量

- **决策输入：** 先列出状态、允许迁移、不可逆终态、金额和数量关系，再为用户命令、定时任务、重复请求和旧 worker 同时发生的场景定义胜者。正确性依赖数据库条件和事务，不依赖进程内时间或缓存锁。
- **仓库例子：** 订单经历待支付、交付、收货、售后、争议、退款与结算等有限状态；库存扣减使用条件更新；退款额度受“成功额 + 预占额不超过实付额”的不变量约束；Outbox 领取使用数据库时间、租约、owner/claim token 与 fencing。支付尝试修正规格还明确一次性创建权和未知结果不得盲目重建请求。
- **防止的失败：** 防止超卖、重复扣减、超过退款额、截止时间两边都成功、旧租约完成覆盖新 owner，以及同一幂等键承载不同请求。
- **验证证据：** [订单 MQ 设计](../superpowers/specs/2026-08-23-order-mq-design.md)、[交易平台设计](../superpowers/specs/2026-08-30-campus-market-design.md) 和 [支付尝试修正规格](../superpowers/specs/2026-09-04-campus-market-payment-attempt-redesign.md) 把状态规则与验收测试写成可执行约束；实验 README 记录并发、重复通知、超时和恢复演练。

## 5. 设计外部依赖与失败语义

- **决策输入：** 对消息、搜索、对象存储、身份公钥、支付和模型服务分别定义超时、重试、幂等、未知结果、降级和恢复动作；同步请求成功不等于下游已完成。
- **仓库例子：** 事务提交后由 Outbox 通过 RabbitMQ publisher confirm 发布，消费者用 Inbox 幂等并在本地事务后 ACK；搜索或读服务不可用返回安全的 503，交易写入不伪造搜索结果；支付 `UNKNOWN` 通过 provider reference 查询与对账收敛；AI 检索或模型无可用依据时返回明确结果或稳定的 503，而不编造规则。
- **防止的失败：** 防止丢消息、重复消费、把下游连接失败记为业务不存在、无限重试放大故障，或把未知支付结果当作失败后重新发起一次扣款。
- **验证证据：** [安全文件服务设计](../superpowers/specs/2026-08-26-secure-file-service-design.md)、实验七设计和实验九设计均包含故障分类；独立实验 README 将 RabbitMQ、Elasticsearch、MinIO、服务发现、模型替身等故障恢复列为验收场景。这里的失败语义是接口契约与恢复证据，而不是生产服务等级承诺。

## 6. 安全、隐私与最小披露

- **决策输入：** 先界定请求者身份、对象归属、外部系统所需字段和日志应排除的字段。访问控制必须在拥有事实的一侧执行，生成模型、前端和反向代理不能成为授权判断的唯一位置。
- **仓库例子：** JWT/RBAC 与对象级 ACL 决定访问范围；不存在和无权访问的私人订单、争议、证据统一为 404。文件下载先检查逻辑授权；实验九由交易服务按 JWT 用户过滤本人资源，AI 服务只取得经授权的最小状态，且不向模型发送 Token、原始私人问题、完整交易对象或写操作工具。
- **防止的失败：** 防止枚举私人资源、泄露对象 key、验证码、支付凭据和敏感日志，也防止提示注入或模型臆测绕开服务端授权。
- **验证证据：** [安全文件服务设计](../superpowers/specs/2026-08-26-secure-file-service-design.md) 规定 ACL、同构 404 和签名下载语义；实验九设计规定来源约束、敏感字段过滤和浏览器 Token 内存生命周期。真实 HTTP 和浏览器用例验证对象边界与最小披露，而不是以 UI 隐藏按钮代替授权。

## 7. 可观测性与人工恢复入口

- **决策输入：** 每个异步或可重建流程都要能回答“目前卡在哪、由谁接管、怎样不破坏不变量地继续”。指标和审计记录应服务于状态判断，不能记录秘密或完整私人内容。
- **仓库例子：** Outbox、索引重建和清理任务使用状态、尝试次数、租约与 token 记录工作归属；消息失败保留可检查终态；索引提供暂停、重放、对账和恢复路径；安全操作有审计，健康、readiness 和结构化指标为服务拆分提供诊断入口。
- **防止的失败：** 防止任务静默卡死、旧 worker 迟到覆盖、索引损坏后只能全量猜测重建，或依靠直接改库、绕过授权的临时处置。
- **验证证据：** [商品读服务设计](../superpowers/specs/2026-09-15-product-read-service-design.md) 说明投影丢失后的保留事件 replay 与接管规则；实验七至九 README 记录故障演练、恢复后的集合核对和健康检查。人工恢复入口只面向受控运维流程，不代表公开业务 API。

## 8. 测试金字塔与真实依赖验收

- **决策输入：** 将纯规则、数据库边界、跨服务契约、故障恢复和浏览器旅程分层验证；越接近外部系统，越要使用隔离的真实依赖，且不能用 skipped 结果替代证据。
- **仓库例子：** 单元测试固定状态机、金额、授权和事件规则；数据库与消息集成测试覆盖条件更新、Outbox/Inbox、幂等和权限；Testcontainers 启动 MySQL、RabbitMQ、Elasticsearch 等真实协作组件；实验九再以 Vitest 和 Playwright 验证前端状态分离、同源代理、桌面与移动浏览器旅程。
- **防止的失败：** 防止 Mock 误掩盖 SQL、编码、容器配置、网络故障、JWT 验签或实际浏览器会话问题，避免“构建成功”被误写为全链路验收。
- **验证证据：** 各独立分支 README 中的 Maven、Testcontainers、前端构建和 Playwright 命令及验收记录，才是相应实验已运行范围的来源；`git diff --check` 与文档链接检查补充保证交付内容本身可审查。

## 9. 实验一至九的演进过程

演进顺序不是把组件简单叠加，而是每一步先保留上一阶段已经证明的边界，再引入新的风险和相应证据。

| 实验 | 新增决策重点 | 延续或新增的验证证据 |
| --- | --- | --- |
| 1 | JWT、RBAC 与可撤销身份基础，先确定认证和授权边界。 | 身份与受保护接口测试。 |
| 2 | 将读取性能与事实修改分开，建立 Cache Aside、失效和热点重建规则。 | 缓存一致性与异常路径测试。 |
| 3 | 面向秒杀和库存竞争，以条件更新、限流、幂等键固定并发规则。 | 并发扣减、重复请求和限流测试。 |
| 4 | 将订单迁移和异步协作拆开，用状态机、Outbox/Inbox、确认与重试表达可靠消息。 | 事务、消息确认、重复消费和故障测试。 |
| 5 | 将搜索确认为派生索引，采用外部版本、重建和修复流程。 | MySQL 与 Elasticsearch 的真实协作及重建验收。 |
| 6 | 将对象存储与逻辑授权分离，处理上传状态、内容校验、ACL、引用计数和清理。 | MySQL、对象存储、真实 HTTP、并发与故障测试。 |
| 7 | 组合为模块化交易单体，统一库存、金额、支付模拟、履约和争议不变量。 | 交易全链路、Testcontainers 和连续恢复演练。 |
| 8 | 在不迁走交易写侧的前提下拆出身份与商品读服务，建立独立数据所有权和版本化事件。 | 多应用真实 HTTP、跨库边界、投影追赶与恢复验收。 |
| 9 | 在全栈客服旅程中加入只读 AI 编排、规则来源约束和前端最小状态。 | 服务端授权、模型替身、Testcontainers、Vitest 与 Playwright 浏览器验收。 |

实验七、八、九的 README 分别展示模块化单体、渐进服务提取、读模型投影和全栈 AI 客服如何衔接；[项目手册入口](README.md) 汇总了这些独立分支的导航与已验收边界。

## 10. 从实验方案走向生产仍缺什么

本仓库是可复现实验，不应把已验收的开发/测试环境描述为生产。以下事项均是未来工作，需在明确业务责任和授权后单独设计、实现和验收：

- 容量规划、压测目标、限额、成本模型和持续性能观测，不能从实验测试规模推导生产承载能力。
- 多可用区或多地域的恢复目标、数据复制、演练、备份保留和灾难恢复切换，不能把单机容器恢复当作多地域恢复。
- 密钥管理、轮换、吊销、审计和硬件/托管边界；仓库中的环境变量占位与本地密钥挂载不构成密钥管理方案。
- 支付、物流、CAS/身份、邮件和模型供应商的真实合同、资质、沙箱到正式环境契约测试与变更管理；目前的模拟或可配置适配器不等同于获准接入。
- 隐私、数据保留、内容安全、交易平台责任、第三方数据处理和正式合规审批，尤其是文件证据、校园身份和 AI 问答相关场景。
- 值班、告警分级、runbook、事件响应、变更发布、补丁管理和长期运营责任。人工恢复入口只有在受控权限、审计和持续演练下才可成为生产操作的一部分。

这些缺口不否定实验的验证价值：它们划清了“代码与测试已证明的行为”和“生产必须补齐的组织、合同与运营能力”，避免把未来工作写成已经实现。
