# 算法、并发控制与可靠性机制

本文只归纳各实验分支已能在实现或测试中找到的行为。它不是生产承诺：组件、事务和队列都只能缩小特定失败窗口，仍要配合观测、恢复与运维决策。

## 1. BCrypt 密码哈希与 SHA-256 高熵令牌摘要

- **解决问题：** 不把可登录密码或可复用的高熵令牌以明文持久化或写入键名。
- **仓库示例：** 身份服务注册时经 `PasswordEncoder.encode` 保存 `password_hash`，登录经 `matches` 校验；验证码/限流维度等使用 SHA-256 摘要。
- **核心步骤：** `保存密码 = BCrypt(原密码)`；`认证 = matches(输入, 已存哈希)`；`键维度 = SHA-256(高熵值或敏感维度)`。
- **正确性不变量：** 认证只能由密码匹配结果决定；摘要仅作不可逆的索引/比对材料，不能当作原值或授权证明。
- **运行代价：** BCrypt 有意增加每次注册和登录的 CPU 时间；摘要为线性输入长度的 CPU 与固定长度存储。
- **优点：** 数据库泄露时不直接暴露原密码；键和日志不必携带敏感原值。
- **缺点：** BCrypt 参数需随硬件能力复审；哈希不阻止在线撞库、重放或已泄露令牌的使用。
- **常见误用：** 用快速 SHA-256 替代密码哈希；把摘要当加密；记录原密码、令牌或可还原材料。

## 2. Cache Aside、提交后失效与空值缓存

- **解决问题：** 降低商品读对数据库的重复压力，同时让缓存失效尽量与已提交数据库状态对齐。
- **仓库示例：** Redis 缓存实验的 `ProductQueryService` 先查缓存再回源；`ProductUpdateService` 在事务 `afterCommit` 中 evict；不存在商品写入短 TTL 空值。
- **核心步骤：** `读：cache -> miss 时 repository -> 写正值/空值`；`写：事务更新数据库 -> afterCommit 删除键`。
- **正确性不变量：** 回滚不删旧缓存；只有提交后才触发删除；空值命中代表“该缓存期内的未找到”，不把依赖故障伪装为未找到。
- **运行代价：** 命中为一次缓存访问；未命中增加数据库访问和缓存写；空值占用受 TTL 限制的存储。
- **优点：** 热读快、负缓存抑制穿透，避免更新前删除把旧值重新填回。
- **缺点：** 提交后删除失败时数据库已无法回滚，短暂陈旧仍可能存在。
- **常见误用：** 数据库更新前删除；将 Redis 异常返回为 404；宣称 after-commit 删除就是分布式事务。

## 3. 热点 Key 重建锁与二次检查

- **解决问题：** 某个过期热点键并发失效时，避免所有请求同时回源。
- **仓库示例：** 生产查询路径使用按商品 ID 的 Redisson `RLock`，最多等待 200ms；取得锁后再次读取缓存，未获锁者也会最后复读。
- **核心步骤：** `miss -> tryLock -> 再查 cache -> 仍 miss 才查库并回填 -> finally unlock`；超时且仍未命中则受控失败。
- **正确性不变量：** 同一键在正常锁服务下只有持锁者执行重建；等待者必须二次检查，释放仅由当前持有者执行。
- **运行代价：** 未命中增加 Redis 锁往返、等待时间和少量锁状态；慢回源仍消耗下游容量。
- **优点：** 跨实例压缩并发回源；watchdog 续租降低慢操作超过固定租期时的重复重建风险。
- **缺点：** Redis/锁不可用或等待超时会牺牲可用性；锁不能修复错误缓存数据。
- **常见误用：** 只在本地 JVM 加锁就宣称多实例协调；漏掉二次检查；无限等待锁。

## 4. Redis Lua 固定时间桶限流

- **解决问题：** 为 AI 支持接口按匿名 IP 或私有用户限制一分钟内的请求数，并保持计数与首次过期设置原子。
- **仓库示例：** `SupportRateLimiter` 以当前 epoch minute 组成键，Lua 执行 `INCR`，第一次计数时 `EXPIRE`，并按匿名 20、私有 10 的每分钟上限判定。
- **核心步骤：** `bucket = epochSecond / 60`；`Lua: count=INCR(key); 若 count=1 则 EXPIRE; return count<=limit`。
- **正确性不变量：** 同一 Redis 键的递增、首次 TTL 和准入判断在一个脚本内完成；键包含维度摘要和分钟编号。
- **运行代价：** 每个请求一次 Redis 脚本；每个活跃维度/分钟一个临时键，空间由 TTL 回收。
- **优点：** 无读改写竞态、实现小、可按用户与 IP 分开配额。
- **缺点：** 分钟交界处可出现两个相邻桶的突发；Redis 故障被显式归类为依赖不可用。
- **常见误用：** 把固定分钟桶误写成别的限流算法；`INCR` 与 `EXPIRE` 分两次执行；只信任可伪造的客户端 IP。

## 5. 条件更新防超卖与乐观并发

- **解决问题：** 多个下单请求竞争有限库存时，不能把库存扣为负数。
- **仓库示例：** 秒杀实验使用 `UPDATE seckill_product SET stock = stock - 1 WHERE id = ? AND stock > 0`，以受影响行数决定能否成交；其他聚合更新也以版本条件保护状态。
- **核心步骤：** `changed = UPDATE ... WHERE stock > 0`；`changed=1 -> 同事务写订单`；`changed=0 -> 售罄`。
- **正确性不变量：** 成功扣减前提是当时 `stock > 0`；扣库存和订单写入在同一事务，失败事务不会留下已扣库存。
- **运行代价：** 一条有条件写及行锁竞争；高热点下冲突请求消耗数据库连接和重试预算。
- **优点：** 不需要先读再写的应用层互斥；受影响行数直接表达业务结果。
- **缺点：** 只保护该库存行，不能自动覆盖支付、外部调用或跨库一致性。
- **常见误用：** 先 SELECT 再无条件 UPDATE；忽略影响行数；将数据库锁当作全链路事务。

## 6. 幂等键、请求摘要与原响应重放

- **解决问题：** 客户端重试和同键并发不能重复创建订单，且同一键被不同请求滥用要被拒绝。
- **仓库示例：** 秒杀服务以 `idempotency_record` 唯一键竞争，在 `READ_COMMITTED` 下用 `FOR UPDATE` 读取终态；相同请求摘要重放原 UTF-8 JSON。
- **核心步骤：** `insert processing(key,digest)`；冲突时 `FOR UPDATE` 读取；`digest 不同 -> 409`，终态则重放；成功时同事务保存响应。
- **正确性不变量：** 一个键只关联一个请求摘要与终态响应；系统失败回滚时记录随事务消失，不留下永久 PROCESSING 阻塞。
- **运行代价：** 一条唯一索引与行锁路径，另有请求摘要和响应正文存储。
- **优点：** 将网络重试转化为确定重放；跨实例依赖数据库约束而非内存状态。
- **缺点：** 大响应增加表存储；真实死锁或锁等待仍需返回可重试冲突。
- **常见误用：** 同键换请求体；重建不同 JSON；把短暂 PROCESSING 当作永久业务状态。

## 7. 有限状态机与截止时间竞争

- **解决问题：** 订单、争议、退款等只能按允许的状态转换，用户动作与到期任务并发时不能得到互相矛盾的终态。
- **仓库示例：** 市场实验定义支付、交付、验收和售后状态；争议更新通过状态集合与 `version` 条件更新，截止任务使用持久 claim。
- **核心步骤：** `读取状态/版本 -> 验证迁移与 now 边界 -> UPDATE ... WHERE state in (...) AND version=? -> 失败则重新读取/拒绝`。
- **正确性不变量：** 终态不可再迁移；每次成功转换满足前置状态与版本；到达截止时刻按已定义的左闭右开边界处理。
- **运行代价：** 状态、版本和截止任务行的持久化；临界点可能出现重试和锁竞争。
- **优点：** 将业务规则表达为可审计的受限图，而非散落的 if；条件写可裁决竞争者。
- **缺点：** 状态和例外增加会膨胀；时间源、时区和任务延迟都需明确处理。
- **常见误用：** 用应用内定时器作唯一事实；无版本条件覆盖他人更新；把超时任务运行延迟误认为截止时间改变。

## 8. Transactional Outbox、Inbox 与至少一次投递

- **解决问题：** 数据库业务提交与 Rabbit 发布不是同一原子操作，消费者也会收到重复消息。
- **仓库示例：** 市场实验把业务事实与 `integration_outbox` 同事务写入；publisher confirm 后才标记发布；消费者以 `(consumerName,eventId)` Inbox 领取，业务修改、Inbox COMPLETED 和派生 Outbox 同事务提交，提交前不 ACK。
- **核心步骤：** `事务写事实+outbox -> dispatcher claim -> publish -> confirm 后标记`；`消费：claim inbox -> 业务+completed+派生 outbox 同事务 -> ACK`。
- **正确性不变量：** 未收到 confirm 的消息不能标记已发布；同一消费者事件只完成一次；ACK 不得先于本地事务提交。
- **运行代价：** Outbox/Inbox 表、轮询、确认等待和重复投递下的幂等检查。
- **优点：** 将不可避免的消息重复变为可收敛状态；broker 停机不阻止本地交易提交。
- **缺点：** 是至少一次，不是端到端恰好一次；积压、毒消息和 confirm 丢失需要恢复流程。
- **常见误用：** HTTP 成功即声称消息已送达；发布前把行标记 PUBLISHED；消费者先 ACK。

## 9. 重试分类、退避、TTL 与 DLX

- **解决问题：** 瞬态网络/依赖失败应可再次尝试，协议或永久错误不能无限消耗队列与计算资源。
- **仓库示例：** 实验五搜索 Outbox 的 `RetrySchedule` 固定为 1s、5s、30s、2m，第四次失败后下一次（第五次）为终态；实验六 `CleanupRetrySchedule` 固定为 5s、30s、2m、10m，`maxAttempts=5`。商品读索引将连接失败、503、408、429 继续重试，永久 ES 4xx 留为 FAILED；消费端三次运行失败进入持久人工失败队列。
- **核心步骤：** `分类 failure -> retryable 则按 attempt 取离散延迟并延后重领 -> 达上限则 FAILED 或人工失败队列`；两套当前计划都是固定阶梯，不是指数公式。替代方案可用 `min(cap, base * 2^attempt)` 并加 jitter；它不是这些路径的现有实现。需要延迟路由时可由 TTL 到期后交给 DLX/目标队列处理。
- **正确性不变量：** 重试只作用于明确可恢复类别；attempt、状态和 owner/token 条件更新一致；实验五、六均在第五次失败后不再重排，避免热循环。
- **运行代价：** 延迟队列/TTL、可用时间与 attempt 的持久记录、重放吞吐和人工处置成本；固定阶梯使等待预算可预估，指数退避的 cap/jitter 则增加配置与测试维度。
- **优点：** 固定阶梯便于审计和故障演练，防止短暂停机立即丢失工作；把不可自动恢复项留下诊断入口。
- **缺点：** TTL/DLX 仅是投递编排，不证明业务成功；固定延迟在大量同时失败时可能形成惊群，指数退避加 jitter 是可选取舍而非当前行为；错误分类会导致过早放弃或无限积压。
- **常见误用：** 对所有异常立即重试；把当前固定阶梯称为指数退避；把 DLX 当作处理完成；不记录 attempt 或不监控人工失败队列。

## 10. 租约、owner token、claim token 与 fencing

- **解决问题：** 进程崩溃后工作可被接管，同时旧 owner 的迟到确认、完成或切换不能污染新 owner。
- **仓库示例：** Outbox、Inbox、索引和重建门禁行均保存 owner、claim token、lease_until；Inbox 的完成/`releaseForRetry` 条件匹配 status、owner 和 claim token（释放还受 attempt 条件约束），不匹配 `lease_until`；重建另加 generation fencing。
- **核心步骤：** `条件 claim(空闲或过期) -> 写 owner+随机 token+lease`；Inbox 的完成/释放按 `status AND owner AND token` 条件更新；接管者以新 token 替换旧 token，换代操作还校验 generation。
- **正确性不变量：** 新 owner 接管并替换 token 后，旧 token 不能推进记录；仅租约过期但尚未接管时，Inbox 的旧 owner 仍可能完成或释放，因为该两条更新不检查 `lease_until`。
- **运行代价：** 额外列、索引和条件更新；长工作需要续租与时钟/数据库时间协调。
- **优点：** 崩溃恢复不靠人工解锁；接管后的迟到回调有 token/generation 拒绝条件。
- **缺点：** 租约过短会重复执行，过长会拖慢接管；租约到期本身不是立刻撤销旧 Inbox worker 的完成/释放权限，fencing 必须被所有下游写路径真正检查。
- **常见误用：** 只保存 owner 不保存不可猜 token；声称 Inbox 完成/释放必验未过期租约；把租约当作永久排他锁。

## 11. Elasticsearch external version、tombstone 与稳定排序

- **解决问题：** 正常发布、重放和乱序消息交错时，旧商品快照不能覆盖新状态或复活已下架结果。
- **仓库示例：** 商品投影按聚合版本写 Elasticsearch；下架或售罄以外部版本写 tombstone；搜索固定 `ON_SALE` 过滤并使用稳定游标排序。
- **核心步骤：** `事件版本 v -> external_gte 写文档/删除标记`；`查询固定过滤+确定性排序 -> search_after`。
- **正确性不变量：** 同一商品较旧版本不覆盖较新版本；tombstone 的版本同样参与比较；翻页顺序必须含稳定的最终 tie-breaker。
- **运行代价：** 外部版本与 tombstone 存储，ES 写入和 PIT/search_after 的外部依赖。
- **优点：** 允许至少一次、乱序重放而不破坏最新投影；稳定排序减少翻页重复/遗漏。
- **缺点：** ES 是读模型而非交易事实；删除标记需要生命周期清理策略。
- **常见误用：** 用接收时间代替聚合版本；物理删除后让旧事件复活文档；只按非唯一字段排序。

## 12. 在线索引重建、高水位补放与原子别名切换

- **解决问题：** 不中断写入地重建搜索索引，并能从中断或别名切换不确定中恢复。
- **仓库示例：** 商品读服务在可重复读快照固定 Outbox sequence 高水位，重放快照后的变化；门禁暂停普通领取，读写别名在一次 ES 更新中切换，意图与清理任务持久化。
- **核心步骤：** `记录目标/代次 -> 快照建新索引 -> 补放至高水位 -> 关门禁并校验 -> 原子切读写别名 -> 按实际别名恢复/清理`。
- **正确性不变量：** 目标名称与切换意图先持久化；旧代不能用过期 generation 切换；清理前确认 live alias 不指向该索引。
- **运行代价：** 双索引并存、快照扫描、补放与 alias API；恢复器和门禁增加运维状态。
- **优点：** 重建期间仍保留可控读写路径；失败可依据持久状态而非猜测恢复。
- **缺点：** 实现与观测复杂；部分切换时必须保持门禁关闭等待收敛。
- **常见误用：** 只重建 ES 而丢失源事件；分两次切读写别名；未核对真实别名就强行 OPEN。

## 13. 内容哈希、引用计数与对象清理

- **解决问题：** 实验六文件服务在数据库事实与对象存储 IO 非原子时恢复上传、清理共享内容，并避免删除仍被逻辑文件引用的 Blob。
- **仓库示例：** 实验六迁移 `V1__file_schema.sql` 定义 `stored_blob(content_hash, reference_count, generation, ...)` 及内容哈希唯一约束；`UploadService`、`UploadTransactionService`、`JdbcBlobRepository`、`JdbcFileAccessRepository` 和 `JdbcCleanupTaskRepository` 分别编排上传、事务状态、引用与清理。实验七/九市场媒体虽有随机 object key 和上传会话，但未实现共享 Blob 的内容哈希/引用计数模型。
- **核心步骤：** 新 Blob 路径为：事务 A `begin` 预留上传会话；临时对象写入并检验后，事务 B `reserve` 将会话标为已验证、按哈希预留/绑定 `STAGING` Blob；事务外 `storage.commit(tempKey, objectKey)` 物理提交；事务 C `finalizeUpload` 将 Blob 置 READY，并创建逻辑 `stored_file`、增加引用、完成会话。若物理提交后事务 C 失败，保留可恢复状态并由恢复扫描收敛。READY Blob 复用由 `reserve` 返回 `ReadyReuse`，直接在事务 `attachReadyBlob`/`finalizeUpload` 创建逻辑文件、增加引用并完成会话，不重复 `storage.commit`。删除是独立路径：仅引用归零且清理 claim 有效时，清理器执行物理删除并完成 Blob/任务。
- **正确性不变量：** `reference_count` 不为负，且只有 READY Blob 才能增加引用；新 Blob 的逻辑文件/引用只在物理 `storage.commit` 后的事务 C 创建；只有引用归零且 generation、object key、清理 token/租约条件仍匹配时才可删除；内容哈希不是对象访问路径。
- **运行代价：** 读取全文件计算哈希、元数据行、清理扫描及对象存储调用。
- **优点：** 实验六支持去重/完整性比对和崩溃后清理；短事务不被网络 IO 拖住。
- **缺点：** 引用计数竞态与存储最终状态都需补偿；大文件哈希有 CPU/IO 成本，且共享 Blob 生命周期比市场媒体会话模型更复杂。
- **常见误用：** 把市场媒体也说成已实现共享 Blob 引用计数；用内容哈希作为暴露的对象键；先删对象再减少引用；在数据库事务内上传。

## 14. 对象级 ACL、同构 404 与短时授权 URL

- **解决问题：** 私有证据和媒体只能由具体案件参与者与被分配管理员访问，同时不泄露对象是否存在。
- **仓库示例：** 证据 ACL 限制买方、卖方和被分配管理员，管理员角色不自动绕过案件 ACL；不存在与无权访问统一为 404；上传会话有到期时间与 claim token。
- **核心步骤：** `认证 -> 查询资源及案件关系 -> ACL 判定 -> 允许时签发短时、限定对象/动作的 URL`；其他情形返回同构 404。
- **正确性不变量：** 授权基于对象/案件关系而非仅角色；URL 到期、范围和对象绑定；无权路径不暴露存在性。
- **运行代价：** 每次授权的数据库关系查询、签名计算和短时 URL 生命周期管理。
- **优点：** 最小权限、减少枚举泄露，存储层可获得时间受限凭据。
- **缺点：** 404 影响诊断；已签发 URL 在到期前仍需被视为可用授权。
- **常见误用：** 仅检查 ADMIN；把长期公开 URL 当私有访问；用 403/404 差异泄露对象。

## 15. 游标分页与有界查询

- **解决问题：** 避免深 OFFSET 扫描、伪造分页位置和无界 replay/批处理对数据库或搜索集群的压力。
- **仓库示例：** `SupportCursor` HMAC 绑定用户、资源类型与 `(createdAt,id)` keyset 位置且限制 512 字节；`JdbcSupportStatusRepository` 按 `created_at DESC,id DESC` 查询 orders、disputes、warranties，后页使用 `created_at < before OR (created_at = before AND id < beforeId)`；产品 replay 单次限制 1～1000 条，索引快照每批最多 500 行。
- **核心步骤：** `签名 cursor(user,type,createdAt,id)`；`校验签名/绑定 -> 对 DESC 使用 WHERE (created_at,id) < cursor -> ORDER BY created_at DESC,id DESC LIMIT n -> 返回下一 cursor`。只有升序排序才对应使用 `>`。
- **正确性不变量：** cursor 不可跨用户/资源类型复用；排序方向、谓词和 UUID tie-breaker 必须一致以形成确定顺序；每次工作量有显式上限。
- **运行代价：** 适当复合索引、HMAC 与每页固定大小；游标不提供随机跳页。
- **优点：** 深页性能更稳定，签名防止客户端随意改位置，有界任务便于续租和恢复。
- **缺点：** 数据变化时页面仍是某一顺序下的前进视图；客户端需保存 cursor。
- **常见误用：** 只 Base64 不签名；对当前 DESC 查询错误使用 `>`；排序缺少唯一 tie-breaker；无上限循环扫描。

## 16. RAG 检索、来源约束与结构化事实隔离

- **解决问题：** AI 支持回答要基于当前公开规则，私有交易事实不能被任意模型提示或规则索引混淆。
- **仓库示例：** 对非空问题，`PolicyRetriever` 先执行 `index.find(question, corpus.version())`，再比较 `aliasVersion` 与语料版本；不一致即抛出不可用异常，否则保留公开来源、同版本、分数至少 0.70 的最多 5 个片段。`AnswerService` 对私有问题先由交易服务按 Bearer 授权读取，再只向模型传安全模板和服务端来源。
- **核心步骤：** `分类问题 -> 私有事实先授权读取 -> index.find(version) -> 比较 aliasVersion -> 过滤 public source/score/limit -> 无足够依据则固定回答 -> 模型仅见已审阅片段`。
- **正确性不变量：** 来源由服务端决定；索引/语料版本不一致即不可用；结构化交易事实不以完整对象外发给模型。
- **运行代价：** ES 检索、版本校验、授权 HTTP 调用和模型外部依赖；版本不一致也已付出一次 `index.find` 的 ES 查询成本，但异常路径不会调用模型；每次检索受 top-k 限制。
- **优点：** 可追溯规则出处，降低过期索引与提示注入扩大上下文的风险。
- **缺点：** 检索不命中会降低回答覆盖率；模型仍非业务事实裁决器。
- **常见误用：** 假定版本会在检索前预检而忽略其查询成本；索引版本不一致仍回答；把 JWT、完整订单或私有对象键送入提示。

## 17. 机制组合时的整体取舍

这些机制将一致性分层：数据库条件写、状态机和幂等记录守住交易事实；缓存、搜索和消息通过失效、Outbox/Inbox、版本与重放做异步收敛；对象与 AI 再以 ACL、签名、来源和最小外发划定安全边界。代价是更多状态表、TTL/租约、版本、队列积压与恢复分支，不能只看单个 HTTP 成功。

可观测性至少需要区分缓存命中/锁忙、Outbox 与 Inbox 的状态和 attempt、租约接管、人工失败队列、投影高水位/门禁/别名，以及对象清理和检索版本失败。恢复时应以持久记录、broker confirm、数据库事实和真实 alias/对象状态交叉核对；重放必须可幂等，旧 owner 与旧版本必须被拒绝。

当前实现的生产化边界同样重要：Redis、RabbitMQ、Elasticsearch、MinIO 和模型服务的故障都可能发生；提交后的缓存删除和异步发布都不是分布式事务；支付与外部物流仍有实验适配边界。未来若要扩展，应先为容量、告警、密钥轮换、灾备、数据保留、人工处置和合规获得独立设计与验证，而不是从本实验结果推导通用生产保证。
