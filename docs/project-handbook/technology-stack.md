# 技术栈、选型依据与优缺点

本目录以各学习分支中已跟踪的 POM、Compose、前端清单和 README 为依据。版本是实验分支的版本，不表示整个仓库使用同一版本；没有在这些证据中核验的版本不在此列出。

## 1. Java、Maven 与 Spring Boot

- **项目职责**：各实验以 Java 17 和 Maven Wrapper 构建 Spring 应用；Web、校验、数据访问、健康检查等由 Spring Boot starter 组合。
- **选择理由**：Java 17 是各分支 POM 明确声明的语言基线，Spring Boot 用约定化依赖和插件降低独立学习实验的启动成本。
- **优点**：同一语言基线便于复用领域与测试经验，Maven 聚合也支持实验八、九的多模块构建。
- **缺点**：跨实验的 Spring Boot 版本并不一致，升级时必须验证依赖兼容性，不能仅凭父 POM 名称推断行为。
- **替代方案**：可在另一个独立实验选择 Gradle 或其他 JVM 框架；这不是当前分支已经实现的迁移计划。
- **边界**：实验一、二、三使用 Spring Boot 3.5.5；实验五、六、七、八使用 3.5.16；实验九的聚合 POM 使用 4.1.1。它们不是全项目统一版本承诺。

## 2. Spring Security、JWT、RS256 与 JWKS

- **项目职责**：实验一实现登录、RBAC 和 refresh token 轮换；实验八、九由身份服务签发 RS256 token，Gateway 与其他服务通过 JWKS 验签。
- **选择理由**：Spring Security 提供 HTTP 认证授权边界，JWT 便于服务间携带经过签名的身份声明，JWKS 让验签方获取公钥而不持有私钥。
- **优点**：权限码可用于接口授权；短期 access token 与可撤销 refresh token 分别覆盖访问和续期；RS256 将签发私钥与验签公钥分离。
- **缺点**：JWT 一经签发难以立即撤销，密钥轮换、issuer/audience 校验和 JWKS 缓存均增加运维与测试复杂度。
- **替代方案**：会话 Cookie、OAuth2 授权服务器或集中式令牌内省可以替代部分场景，但仓库未实现这些替换方案。
- **边界**：实验七、八、九只保留 CAS 适配端口，不把它描述为校方正式身份认证；客户端经 Gateway 访问，服务内部地址不是公开客户端契约。

## 3. MySQL、JDBC 与 Flyway

- **项目职责**：MySQL 保存用户、RBAC、商品、订单、库存、金额、Outbox/Inbox 与服务拆分后的各自数据；JDBC 承担明确 SQL 访问，Flyway 执行建表和演进迁移。
- **选择理由**：交易状态、金额和截止时间需要事务与约束，关系数据库适合作为这些事实的持久化位置。
- **优点**：事务可让业务事实与 Outbox 一起提交；SQL、锁顺序和乐观版本控制可被直接审查；Flyway 使新环境能按版本建立结构。
- **缺点**：跨服务事务不会因拆分而自动成立，模式演进、索引和锁竞争都需要单独设计与验证。
- **替代方案**：可用 ORM 降低样板代码，或在其他系统选择分布式数据库；这些替代不改变本仓库以 MySQL 事实源为核心的实现。
- **边界**：Redis、Elasticsearch 和 MinIO 不承担订单、库存或金额正确性证明；实验八、九的 identity、交易与商品读库彼此隔离，不能跨库直接当公共 API 使用。

## 4. Redis、Redisson 与 Lua

- **项目职责**：实验二实现 Cache Aside、提交后失效和热点键重建锁；后续实验把 Redis 用于验证码、缓存或限流。
- **选择理由**：Redis 适合低延迟缓存和原子计数，Redisson 的 RLock 可协调多 JVM 的热点缓存重建。
- **优点**：Cache Aside 降低重复读压力；提交后删除缓存使失效对齐已提交事务；Redisson 支持跨实例二次检查与锁协调。
- **缺点**：缓存失效失败不能回滚已提交数据库事务；分布式锁不能替代下游容量保护或一致性设计。
- **替代方案**：本地锁只适合单 JVM 对照；也可用消息驱动失效或其他缓存产品，但它们没有在本实验中实现为主路径。
- **边界**：实验九客服限流是 Lua 原子 `INCR` 加首次 `EXPIRE` 的固定分钟桶，不是滑动窗口或令牌桶；Redis 失效时不应被当作交易事实源。

## 5. RabbitMQ 与 Spring AMQP

- **项目职责**：实验七至九用 RabbitMQ 在事务 Outbox、消费者 Inbox 和商品读投影之间传递事件，Spring AMQP 负责应用侧集成。
- **选择理由**：异步事件可把交易提交与读模型更新解耦，并在外部依赖短暂故障时保留可恢复的待发布事实。
- **优点**：publisher confirm、Inbox 幂等、人工失败副本和租约/claim-token fencing 共同降低重复投递和抢占风险。
- **缺点**：至少一次投递意味着消费者必须幂等，消息延迟也使读模型不是同步更新结果。
- **替代方案**：可改用其他消息系统或同步调用；同步调用会收紧可用性耦合，其他消息系统未在仓库实现。
- **边界**：HTTP 写成功仅表示业务事实与 Outbox 已提交，不能表示消息已被消费或 Elasticsearch 已完成更新；RabbitMQ 不是分布式事务协调器。

## 6. Elasticsearch 与 SmartCN

- **项目职责**：实验五及后续实验将商品搜索作为可重建读模型，使用 SmartCN 分词、读写别名、Outbox 投递和外部版本控制。
- **选择理由**：MySQL 事务查询不适合中文全文检索与高亮、聚合等搜索能力，SmartCN 覆盖实验中的中文商品文本检索。
- **优点**：搜索与交易写模型分离；`external_gte`、tombstone 和别名切换帮助处理重复事件、删除和在线重建。
- **缺点**：索引会与事实源异步收敛，索引不可用时搜索需要显式失败处理，维护重建流程也更复杂。
- **替代方案**：可只用 MySQL 条件查询，或选用其他检索引擎；这些方案无法直接获得当前实现的 SmartCN 索引流程。
- **边界**：MySQL 仍是商品与交易事实源；搜索固定过滤在售状态，读写别名必须指向同一物理索引，别名异常时实现应拒绝猜测修复。

## 7. MinIO 与对象存储

- **项目职责**：实验六至九以 MinIO 保存私有商品媒体、争议或质保证据；数据库保存授权和上传绑定事实。
- **选择理由**：对象存储适合大文件 IO，避免把媒体直接放进交易表，同时保留 S3 风格客户端集成方式。
- **优点**：对象 key 随机化且不携带业务身份；Tika 和文件签名共同校验内容类型；持久清理任务可处理事务外 IO 的失败收敛。
- **缺点**：对象写入与数据库事务无法原子提交，需要补偿、清理和故障演练；存储本身也不表达谁有读取权限。
- **替代方案**：本地文件系统或云对象存储可以替换 MinIO，但需要重新实现授权、清理和故障边界。
- **边界**：逻辑 ACL 由 MySQL 决定，管理员角色不会自动绕过案件 ACL；数据库事务期间不做 MinIO IO，存储故障不能被伪装成资源不存在。

## 8. Spring Cloud、Eureka 与 Gateway

- **项目职责**：实验八把身份、兼容交易、商品读、发现与网关拆分为独立应用；实验九在该结构上增加 AI 服务。
- **选择理由**：Eureka 提供实验中的服务发现，Gateway 给客户端提供单一入口并减少直接暴露内部服务。
- **优点**：身份与商品读服务可独立演进，Gateway 集中路由和验签边界，独立数据库避免跨模块直连表。
- **缺点**：拆分引入服务注册、启动顺序、网络故障和版本兼容等额外复杂度，排障面大于模块化单体。
- **替代方案**：可维持模块化单体或采用其他注册与网关技术；它们不是该仓库已实现的迁移结果。
- **边界**：实验八的 Spring Cloud BOM 是 2025.0.3，实验九是 2025.1.3；README 明确该拆分只支持全新环境，不把它描述为不停机迁移能力。

## 9. Spring AI、RAG 与模型适配器

- **项目职责**：实验九的独立 AI 客服服务检索已审阅公开规则，并对已授权的本人订单、争议和质保状态进行只读编排回答。
- **选择理由**：Spring AI 2.0.1 提供 OpenAI 兼容模型适配边界，检索与固定安全模板把模型输入限制在预期范围。
- **优点**：模型供应商可通过服务端配置切换；公开规则索引和固定模板有助于避免把 token 或完整交易对象发给模型。
- **缺点**：模型输出仍可能不稳定，远程模型依赖会失败或超时，检索质量依赖已审阅规则与索引状态。
- **替代方案**：可只返回规则检索结果，或接入另一个获准的模型适配器；模型不能替代交易领域服务的授权与状态机。
- **边界**：RAG 在此仅服务于已审阅公开规则；不向模型提供交易写工具、任意私人问题或 token，也不把模型回答作为自动退款或仲裁决定。

## 10. React、TypeScript、Vite 与 Nginx

- **项目职责**：实验九的 `support-web` 用 React 客服界面承载浏览器旅程，TypeScript 编译、Vite 构建，容器中的 Nginx 提供静态站点并代理 Gateway。
- **选择理由**：React 适合交互式单页界面，TypeScript 提供编译期约束，Vite 提供开发和构建工具链，Nginx 保持浏览器到 Gateway 的同源入口。
- **优点**：前端可独立进行单测、构建和端到端验证；静态站点不需要持有内部服务凭据。
- **缺点**：前后端类型和鉴权边界仍需协同维护，构建期与浏览器运行期问题也可能分别出现。
- **替代方案**：可选择其他前端框架、SSR 或由后端渲染页面；这些并非当前客服站点的实现。
- **边界**：`package.json` 记录 React 19.3.0、TypeScript 5.9.3、Vite 8.3.0，且 Node 引擎要求 `^20.19.0 || ^22.12.0 || >=24.0.0`；这些版本仅属于实验九前端。

## 11. Docker Compose、Testcontainers、JUnit、Vitest 与 Playwright

- **项目职责**：Compose 启动实验所需基础设施和多应用 smoke 环境；JUnit/Testcontainers 验证 Java 与真实依赖协作；Vitest 和 Playwright 验证前端逻辑与浏览器旅程。
- **选择理由**：可重复的容器环境减少手工依赖差异，分层测试让服务逻辑、集成边界和浏览器会话分别可验证。
- **优点**：Testcontainers 将 MySQL、RabbitMQ、Elasticsearch 等测试依赖隔离；Playwright 覆盖桌面与移动浏览器旅程；Compose 使本地演示拓扑可见。
- **缺点**：Docker 资源、镜像和启动时间会影响测试；Compose 的启动顺序不等价于服务就绪，端到端测试成本也更高。
- **替代方案**：可使用纯 mock 或手工环境，但不能据此替代真实依赖交互的验收证据。
- **边界**：POM 管理的 Testcontainers 版本为 1.21.4；实验九前端清单包含 Vitest 5.0.1 和 Playwright 1.63.0。Docker 不可用或测试被跳过不能被写成完整外部协作验证。

## 12. Prometheus、Grafana、Micrometer 与 k6

- **项目职责**：Micrometer 和 Actuator 暴露低基数指标；实验二的可选 Compose 监控栈包含 Prometheus 与 Grafana，k6 脚本用于热点商品请求压测。
- **选择理由**：指标能观察缓存命中、回源、锁等待和故障积压，k6 让固定场景下的本地回归比较可脚本化。
- **优点**：Prometheus 可采集或接收指标，Grafana 可查看持久化看板，Micrometer 避免应用直接绑定单一后端。
- **缺点**：指标需要标签治理、告警设计和容量规划；本地压测受机器与依赖状态影响，不能直接外推。
- **替代方案**：可使用其他监控后端或浏览器 Dashboard；这些选择不自动提供长期存储和跨环境基线。
- **边界**：实验二 Compose 记录 Prometheus 3.5.0 与 Grafana 12.1.0；k6 阈值仅用于本机开发回归，不能作为服务等级承诺，也不能凭脚本存在声称已完成压测。

## 13. 选型总结与适用边界

这组实验以 MySQL 事务事实、Flyway 演进、Redis 辅助状态、Outbox/Inbox 事件、可重建 Elasticsearch 读模型和私有对象存储形成组合：交易写模型优先保证可审查的事实，异步组件承担可恢复的派生工作。Spring Cloud 在实验八、九演示从模块化单体到有限服务拆分，AI 服务再把检索和模型调用限制在只读、已授权、已审阅的边界内。

代价是版本分叉、容器依赖、异步一致性、索引重建、密钥轮换和多服务排障都需要持续验证；缓存、消息、搜索、模型和对象存储都不能替代数据库中的交易正确性。适合用作 Java/Spring 的设计、测试、故障恢复与面试讨论材料，不应把学习实验直接表述为已具备完整生产化条件。仍需在实际部署前补齐环境配置治理、密钥与证书生命周期、容量与告警、备份恢复、合规评估、真实外部服务资质以及针对目标环境的安全与性能验证。
